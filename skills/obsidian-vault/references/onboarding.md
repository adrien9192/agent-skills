# Contextual onboarding

Prepare useful working context in the existing vault, not a second folder tree.

## Read before asking

Resolve the named project/client, read its hub and directly linked context, and inspect relevant
repo documents. For a general personal intake, use existing dashboard/context notes; put an
unfinished intake in `50-Inbox` rather than inventing a project or rewriting global rules.

Build a compact internal coverage table: known fact, exact source/date, gap or conflict.
Cover these seven areas without automatically asking seven questions:

1. Role and activity.
2. Clients, collaborators and decision owners.
3. Current priorities, horizon and observable success.
4. Tools and existing access routes.
5. Repeated friction or wasted effort.
6. Writing preferences, using only supplied or authorized examples.
7. Permission boundaries and actions requiring human approval.

Read tool availability/configuration without exposing secrets. A listed connector does not prove
a logged-in session. Record only the access route, last read-only check and missing prerequisite.
Do not configure accounts, import credentials or trigger client-facing actions during intake.

## Fill only the gaps

Show the useful known context in at most five lines. Ask one unresolved question at a time,
numbered within a maximum of seven questions for this intake. Do not re-ask an answer available
in current sources. Clarify contradictions that inspection cannot resolve. If there is no useful
gap, finish immediately instead of conducting a ceremonial interview.

When answers are needed, use [the recorded interview](interview.md): save the question before
asking and the answer before continuing. “Stop”, “termine” or “pause” ends the questions now.
An onboarding request is permission to organize its context, not to relax the user's boundaries.

## Put information in its existing home

- Identity, activity, priorities and stakeholders: the relevant project/client hub.
- Tools: a small “Accès” section in that hub, or link the existing stack/tool inventory. Never
  duplicate the entire skill catalog, all settings or private credentials.
- Writing: link existing voice/style sources. Do not turn one client's tone into a global rule.
- Boundaries: cite the authoritative rules; record additional task-specific constraints locally.
  Never replace AGENTS, CLAUDE or a configuration file with generated onboarding rules.
- Missing, tentative or unconfirmed information stays explicitly pending, with its source/owner.

Close with paths updated, remaining unknowns and one next useful action. Test retrieval with a
question drawn from the actual need: answer it using a saved note and its source. If the data are
still missing, show the missing prerequisite instead of inventing a successful onboarding.
